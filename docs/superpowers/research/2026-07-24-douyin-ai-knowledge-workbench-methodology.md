## 1. 视频的可执行方法论

视频不是把 Obsidian 当作“笔记仓库”，而是把它作为可阅读、可连接、可审阅的知识 IDE。AI 的职责不是填充模板，而是基于明确的目录语义和当前项目上下文，完成以下闭环：

1. 接住尚未消化的信息与灵感。
2. 将新信息连接到既有资产、进行中的项目和历史输出。
3. 追问当前判断、流程或方法是否已经过时，形成可验证的更新假设。
4. 将结论变成下一步行动、项目上下文或可复用方法。
5. 将实际输出和复盘再次送回知识库，使下一轮判断有真实反馈，而不是重复套用模板。

目录语义对应 PARA 的基本结构，并补齐两个 AI 工作所需的区域：

| 视频工作台语义 | 目的 | BSC/Obsidian 落点 |
| --- | --- | --- |
| Projects | 当前目标、约束、风险和验收 | `03_Projects/active/` |
| Assets | 整理过、可复用、仍保留证据边界的材料 | `02_Assets/curated/` |
| Resources | 外部原始资料及来源 | `01_Sources/`、`raw/` |
| Archive | 不应参与当前自动化循环的历史材料 | `05_Archive/reviewed/` |
| Inbox / Inspiration | 尚未消化的输入 | `00_Inbox/`、`inbox/` |
| Skills / Methods | 候选方法与经过验证的复用能力 | `06_Skills/candidates/`、`methods/` |
| Outputs | 已交付文章、报告、脚本与复盘 | `04_Outputs/`、`outputs/` |
| Governed Wiki | 经过来源、提案、lint、评测和发布的事实型知识 | `wiki/` |

关键原则是“知识要反过来检查正在进行的工作”。目录存在并不代表内容已经被理解或采纳，任何从资料到结论的跃迁都必须保留来源、评测和版本记录。

## 2. 对 BSC 的实现映射

### A. 资料与灵感进入不可变证据层

`00_Inbox/`、`01_Sources/`、`02_Assets/`、`03_Projects/active/` 和 `06_Skills/candidates/` 已在工作区初始化。`ObsidianPluginManifest` 和 `WikiSyncService` 会从声明的项目范围内捕获真实文件，并为资料分配 `inspiration`、`source`、`asset`、`project_context` 或 `skill_candidate` 角色。`05_Archive/`、当前 `wiki/`、输出和蒸馏目录保持排除，避免反复摄入自身生成物。

原始内容进入 BSC 后由 `SourceRecord` 保存其身份、来源、信任等级、状态与捕获时间。它不是可被 Wiki 覆盖的草稿；对外部插件的导出仍处于验证/复核状态，不能直接提升为事实。

### B. 从资料到知识，而不是直接写文件

资料只能通过 `WikiProposal` 进入 `wiki/`：提案声明操作和引用来源，`WikiLint` 验证引用、路径、结构和冲突，`WikiEvaluator` 用项目评测用例衡量是否退化，`ProposalGate` 最后发布并保留修订与回滚路径。`CitationLink` 与知识图关系由发布过程投影；检索索引是派生物，可重建，不是事实权威。

这使得 AI 的“连接”有可审查边界：它可以建议关联、提出已过时的判断和创建补丁，但不能把未经来源支持的内容伪装成已掌握的知识。

### C. 从当前项目定制 SOP 与 Skill

`03_Projects/active/` 是定制化的核心输入。它与可复用的 `02_Assets/` 和候选 `06_Skills/candidates/` 同步为有类型的上下文，而不是强制套一份通用 PRD/SOP 模板。`AGENTS.md` 规定了该项目可访问目录、来源要求、提案路径和发布边界。

候选方法不自动晋升。只有在真实输出或反馈中证明有效、保留适格 A/B 层证据、通过方法提案与评测后，才可进入 `methods/`。因此 Skill 库是经结果验证后的可复用能力，而不是提示词堆放区。

### D. 产出回流与定期蒸馏

`04_Outputs/` 与 `outputs/` 中的真实交付物被注册为不可变 D 层输出。已接受或已归档的产出可以作为“风格或结果样本”进入有界上下文，但不会被当作事实证据。每日增长循环完成捕获、分诊、上下文构造和蒸馏；周蒸馏会生成受管理的周度产物及清单。失败、模型不可用或模型响应不合格时，运行会记录确定性降级原因，不会声称已经调用或生成。

默认计划采用 `Asia/Shanghai`：资料同步 17:00、Horizon 捕获 17:05、Wiki 维护 17:15、增长循环 17:25、周蒸馏周五 17:40。调度记录、运行事件、重试和恢复由 BSC 持久化；Obsidian 仍负责呈现和人工审阅。

## 5. 尚需真实操作触发的外部边界

本次没有执行、读取或修改第三方 Obsidian 插件代码。插件桥接只会在插件真实导出文件到已声明的项目路径后，显示为已捕获；目前的 `awaiting_export` 状态是诚实的准备就绪状态，不是已同步声明。

后续日常使用应是：在 Obsidian 插件或手工目录产生真实资料/输出 -> 由增长循环捕获 -> 在 Studio 审阅提案和来源 -> 发布合格知识 -> 从当前项目上下文生成定制 SOP 或内容 -> 将实际结果回流。这样才保留了视频方法论中“工作检查知识、知识反过来改进工作”的循环，而非单次导入或模板化写作。
